# Studio OS

Подготовка текущей версии к Railway/Supabase: [DEPLOYMENT](docs/DEPLOYMENT.md). Используется release/production-review, без merge в main. Docker-сборка не требует секретов; перед запуском применяются миграции и повторяемый seed.

Studio OS: Next.js App Router, TypeScript strict, Tailwind CSS, PostgreSQL/Prisma и pnpm. Реализованы дизайн-система, база данных, защищённый вход сотрудников и рабочий каталог. Остальные бизнес-разделы пока — заглушки.

## Локальный запуск

Требуются Node.js 22.12+ (рекомендуется Node.js 24 LTS) и pnpm 11.25.0.

```sh
pnpm install --frozen-lockfile
cp .env.example .env
# Задайте DATABASE_URL и APP_ORIGIN в .env.
pnpm db:migrate
pnpm db:seed
pnpm dev
```

Откройте http://localhost:3000. Каталог и админка требуют БД; сборка и модульные тесты подключение к ней не используют.
Для миграции и seed скопируйте `.env.example` в `.env` и задайте `DATABASE_URL` от единственного Supabase PostgreSQL.
Пример содержит только заполнители. Не коммитьте реальный `.env`.

## Команды

| Команда | Назначение |
| --- | --- |
| `pnpm dev` | Локальный сервер Next.js |
| `pnpm build` | Production-сборка |
| `pnpm start` | Локальный запуск готовой сборки |
| `pnpm lint` | ESLint, включая границы UI/server |
| `pnpm typecheck` | Генерация типов маршрутов и TypeScript strict |
| `pnpm test` | Vitest: проверки серверной границы |
| `pnpm test:watch` | Тесты в режиме наблюдения |
| `pnpm test:routes` | Запуск production-сервера, HTTP-проверка маршрутов и остановка (после build) |
| `pnpm db:validate` | Проверка схемы Prisma без обращения к БД |
| `pnpm db:generate` | Генерация Prisma Client |
| `pnpm db:migrate` | Применение версионированных миграций |
| `pnpm db:seed` | Безопасное заполнение справочников |
| `pnpm db:test` | Интеграционная проверка на отдельной пустой DATABASE_TEST_URL |

Prisma Client генерируется перед dev/build/typecheck/test и seed. Динамические страницы каталога и админки используют серверные адаптеры к единому прикладному слою.
Для проверки dev-сервера: `pnpm test:routes --dev`. Используются локальные порты 3100/3101; сервер останавливается после проверки.
Установка движка Prisma разрешена для миграций; автоматический postinstall Prisma отключён. Генерация явно управляется скриптами проекта.

## Маршруты

`/`, `/catalog`, `/catalog/[slug]`, `/configure/[slug]` (например `/configure/a4`), `/cart`, `/orders`, `/mini`, `/admin`, `/admin/catalog`.
Карточка каталога ищет активный товар в БД; /configure/[slug] пока показывает оболочку без расчёта.
Админка защищена; /admin/login — вход для сотрудников. Заказы и производственная доска пока не подключены.

## Структура

- `app/(public)` — публичные маршруты и layout; `app/admin` — отдельный layout админки.
- `components` — представление; интерактивная навигация явно помечена `use client`.
- `lib` — общие browser-safe модули без секретов и бизнес-правил.
- `server` — серверная граница с `server-only`, будущий единый прикладной слой.
- `prisma` — схема PostgreSQL; `tests` — Vitest.

Сборка и dev используют поддерживаемый Webpack-режим, чтобы PostgreSQL-драйвер работал на Windows без служебных junction/symlink. Выходной каталог — .next-auth (игнорируется); старый .next не используется.

pnpm настроен на hoisted node_modules и локальный игнорируемый store для установки на Windows без привилегии создания symlink.
Кеш также локален и игнорируется. ESLint 9.39.5 выбран из-за peer-ограничений плагинов eslint-config-next; реестр помечает ветку 9 устаревшей. Переход на ESLint 10 требует совместимых версий этих плагинов.

## Размещение и ограничения

Текущая версия подготовлена для Node.js в Railway с Supabase; фактический статус размещения — в PROGRESS. Используются динамические SSR-маршруты.
Cloudflare остаётся целевой площадкой интерфейса. Перед размещением потребуется отдельный выбор: статическая генерация известных slug либо проверенный Cloudflare-адаптер и обоснование Workers для динамических маршрутов.
Не считать стандартную Node-сборку готовым артефактом Cloudflare Pages.
Prisma и будущая бизнес-логика остаются в едином Node.js backend; не дублировать их в Next.js API/Actions и боте.
Supabase — единственный PostgreSQL и владелец пользовательских файлов (Storage). Railway рассматривается для общего backend/бота; сервисы сейчас не создаются.

## Дизайн-система — этап 2

Общие токены и компоненты используются сайтом, Mini App и админкой. Акцент #7C3AED, системный шрифтовой стек с Inter/Segoe UI, адаптивные сетки и видимый фокус. UI-библиотеки не добавлялись.
Витрина доступна на /ui-kit только через pnpm dev; в production маршрут возвращает 404.
Описание API компонентов, состояний и доступности: [DESIGN_SYSTEM](docs/DESIGN_SYSTEM.md).
Mini App имеет отдельную оболочку и нижнюю навигацию по демонстрационным вкладкам; Telegram и бизнес-функции по-прежнему не подключены.

## База данных — этап 3

[DATABASE](docs/DATABASE.md) описывает связи, точные деньги, версии прайсов, snapshot и порядок проверки. Источник требований — предоставленное пользователем [ТЗ](docs/STUDIO_OS_MVP_TZ.md).
Seed создаёт только A4/A3 и три недоступных демонстрационных материала, не меняя существующие записи. Реальные цены, оборудование, пользователи и персональные данные отсутствуют.
Проверяйте миграцию через migrate deploy; db push не переносит дополнительные SQL-ограничения. На этапе 3 API и интерфейсы не создавались.

## Авторизация сотрудников — этап 4

[AUTH](docs/AUTH.md): /admin/login, роли ADMIN/OPERATOR, отзывные HttpOnly-сессии, серверные права, лимиты входа и аудит.
Перед запуском задайте DATABASE_URL и точный APP_ORIGIN, затем выполните pnpm db:migrate.
Первый администратор создаётся через pnpm admin:bootstrap с ADMIN_EMAIL/ADMIN_PASSWORD из защищённого окружения. Известного пароля по умолчанию нет; команда не заменяет существующую учётную запись и повторно не создаёт администратора.
В production APP_ORIGIN обязательно использует HTTPS. Telegram-вход и публичная регистрация сотрудников не реализованы.

## Рабочий каталог — этап 5

После pnpm db:migrate и pnpm db:seed доступны пять начальных изделий на /catalog, поиск, категории и /catalog/[slug]. Seed повторяем и сохраняет изменения администратора; материалы помечены «под заказ», начальные изображения — иллюстрации.
Управление: /admin/catalog. ADMIN может создавать и редактировать товары; OPERATOR требует catalog:write для записи. Изображения задаются HTTPS-ссылками с подписями. Изменения появляются на сайте без сборки.
Режимы AUTO_SHEET/MANUAL_REQUEST заданы явно; калькулятор, приём заявок и e-commerce пока не подключены. Инструкции и проверки: [CATALOG](docs/CATALOG.md).
