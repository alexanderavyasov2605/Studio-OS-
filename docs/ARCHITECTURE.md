# Архитектура MVP

Статус: проектное предложение от 2026-11-03; на этапе 1 реализованы только маршруты и layout. [Решения](DECISIONS.md), [источник требований и вопросы](PROGRESS.md).

Техническая основа: Next.js App Router, TypeScript strict, Tailwind CSS, pnpm; Prisma/PostgreSQL без моделей. app/(public), app/mini и app/admin разделяют layout. components содержит представление, lib — browser-safe данные, server — единую будущую серверную логику с server-only. Страницы не обращаются к БД. Клиентские компоненты управляют только представлением: навигацией, полями, вкладками и диалогами.

Этап 2 добавляет общую [дизайн-систему](DESIGN_SYSTEM.md) и dev-витрину /ui-kit. Описанные ниже серверные границы и владельцы данных остаются прежними.

## Границы и данные
| Компонент | Ответственность |
| --- | --- |
| Cloudflare, статический интерфейс | Сайт, Telegram Mini App, админка; предварительный калькулятор и представление доски |
| Общий Node.js backend, план Railway | Авторизация, цена, тарифы, заказы, версии/согласования, переходы производства, обработка Telegram |
| Telegram-бот в том же backend | Команды, ссылки Mini App, уведомления через общий прикладной слой |
| Supabase PostgreSQL | Единственный источник структурированных данных |
| Supabase Storage | Единственное хранилище пользовательских файлов; приватные bucket |
| Supabase Auth, если потребуется | Вход сайта/сотрудников; связь с внутренними пользователями |

Поток: интерфейс → HTTPS API → прикладной слой → PostgreSQL/Storage.
Telegram → проверенный webhook → тот же прикладной слой. Веб-клиенты не записывают бизнес-данные напрямую в БД. Workers, R2, отдельный bot backend, вторая БД и отдельная очередь на старте не предусмотрены.

## Сценарии и модель
- Калькулятор: A4/A3, количество листов и ставка за лист. Дополнительные параметры и точная формула требуют согласования. Админ управляет версиями тарифов; изменение не переписывает существующие заказы.
- Заказ: сервер валидирует входные параметры и доступ, выбирает действующий тариф и рассчитывает сумму. При создании транзакционно сохраняет позиции, snapshot ставок/формулы/валюты/округления и итог. Денежные значения — фиксированная точность или минимальные единицы, не floating point. Переоценка — явное действие с историей, не скрытое обновление.
- Макет: файл связан с заказом и неизменяемой версией; согласование хранит автора, время и конкретную версию. Загрузка новой версии не переносит старое согласие. Переход в производство проверяет актуальное согласование на сервере.
- Доска: минимальные предлагаемые состояния «новый → подготовка → ожидает согласования → производство → готов → завершён», отмена отдельно. Это предложение; согласовать допустимые переходы и ограничения до кода.
- Кандидаты сущностей: User, RoleAssignment, TelegramIdentity, TariffVersion, Order, OrderItem, PriceSnapshot, AssetVersion, Approval, StatusEvent, NotificationOutbox. Схема/миграции пока не создаются.

## Защита и надёжность
- Mini App передаёт исходный initData на сервер. Проверить подпись по алгоритму Telegram, срок auth_date, отклонить подменённые/просроченные данные; initDataUnsafe не является доверенным источником. После проверки выдаётся короткоживущая сессия, повторные обмены ограничиваются.
- Предлагаемые роли: клиент — свои заказы/макеты; менеджер — сопровождение; производство — необходимая часть заказа и доска; админ — тарифы/роли. Точная матрица согласуется. Каждый API проверяет и роль, и доступ к объекту; запрет по умолчанию.
- Проверять сессии/токены на сервере; секрет webhook Telegram, CORS по разрешённым origin, защита от CSRF при cookie-сессиях, ограничения частоты, валидация входа. Идемпотентность создания заказа, webhook и согласования; конкурентное изменение статусов — с проверкой версии.
- Для файлов: ограничение размера/типа, случайные ключи, проверка фактического содержимого и карантин до допуска. Ссылки на скачивание короткоживущие, после проверки заказа; не использовать Telegram как архив. RLS и политики Storage — дополнительный барьер. Service role обходит RLS, поэтому сервер обязан проверять права сам.
- Логи без токенов, initData и содержимого файлов; аудит тарифов, ролей, согласований и статусов. Минимизировать персональные данные. Политику удаления и резервирования БД/файлов согласовать и проверить восстановлением перед production.
- Повтор уведомления не должен повторять бизнес-операцию. При необходимости надёжной доставки использовать outbox в том же PostgreSQL, без нового сервиса.

## Критерии будущей проверки
Подмена клиентской цены не меняет серверный итог; новый тариф не меняет snapshot старого заказа; пользователь не видит чужие заказы/файлы; поддельный/просроченный initData отвергается; старая версия не разрешает производство новой; повтор webhook/запроса не создаёт дубликат; конкурентные переходы не обходят правила.
