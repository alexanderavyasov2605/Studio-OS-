# Авторизация сотрудников — этап 4

Единый Node.js-модуль server/auth владеет паролями, сессиями, правами и аудитом. Next.js Proxy, страницы и Route Handler — адаптеры к нему. Дополнение: [Telegram Login](TELEGRAM_AUTH.md) и клиентская сессия. Публичной регистрации сотрудников нет; ниже сохранён контракт password-входа этапа 4.

## Роли и права
- Вход разрешён активному User с отдельной AdminCredential и ролью ADMIN или OPERATOR. Остальные роли MVP не дают доступ автоматически.
- ADMIN имеет поддерживаемые права админки. OPERATOR по умолчанию читает защищённую оболочку и свою сессию; изменение тарифа требует явного User.permissions: tariffs:write.
- Роли/permissions берутся заново из PostgreSQL, не из формы, cookie, заголовков или клиентского состояния. API изменения ролей отсутствует; неизвестные поля отклоняются. Email при доверенном создании нормализуется trim/lowercase, вход использует точное равенство без LIKE-шаблонов.
- Proxy закрывает все /admin/** и /api/admin/**, кроме точных точек входа /admin/login и auth/login/logout. Страница и обработчик повторно проверяют сессию; мутация повторяет права под блокировками User/AdminSession в транзакции.

## Пароли и сессии
- scrypt N=131072, r=8, p=1; независимая соль 16 байт, ключ 64 байта, сравнение timingSafeEqual. Параметры при проверке ограничены поддерживаемым форматом. Для отсутствующего/повреждённого хеша выполняется та же дорогая проверка.
- CLI требует минимум 16 символов, максимум 256 UTF-8 байт, без скрытого обрезания пароля. Одновременно выполняются не более 2 scrypt, очередь ограничена.
- Сессия: 32 случайных байта, срок 8 часов без автоматического продления. В БД только SHA-256 токена; токен передаётся исключительно в cookie и не возвращается JSON-ответом.
- Cookie HttpOnly, SameSite=Strict, Path=/, без Domain. В production — Secure и имя __Host-studio_admin. HTTP допускается только для локальной разработки; HTTPS-development также ставит Secure.
- Logout — только POST с проверкой Origin; отзыв и аудит атомарны. Удаление cookie не заменяет отзыв: повтор токена после выхода получает 401. Версия Credential, блокировка User и актуальные роли проверяются на каждом запросе.
- Ответы админки/API: private, no-store, Vary Cookie, noindex, DENY для frame. После входа/выхода выполняется полная навигация для очистки клиентского кэша интерфейса.

## Первый администратор
1. Применить миграции: pnpm db:migrate.
2. Передать ADMIN_EMAIL и уникальный ADMIN_PASSWORD через окружение/секрет-хранилище. Пароль не передавать аргументом команды, не коммитить и не записывать в историю shell.
3. Выполнить pnpm admin:bootstrap. CLI нормализует email, хеширует пароль и атомарно создаёт User/ADMIN, Credential и AuditLog.
4. Удалить переменные bootstrap из окружения после выполнения.

Команда не имеет известного пароля по умолчанию, не повышает роль существующего User и отказывается работать после появления любой Credential. Блокировка PostgreSQL защищает от параллельного bootstrap. Создание других сотрудников, сброс пароля и интерфейс управления ролями не входят в этап.

## HTTP-контракт
| Метод | Адрес | Защита |
| --- | --- | --- |
| POST | /api/admin/auth/login | Точный Origin, JSON email/password, лимиты, одинаковая ошибка для неверного пароля/неизвестного email |
| POST | /api/admin/auth/logout | Точный Origin, отзыв текущего токена и очистка cookie; повтор безопасен |
| GET | /api/admin/session | Активная сессия, только безопасные данные текущего сотрудника |
| PATCH | /api/admin/tariffs/:id | Сессия, tariffs:write, Origin; только pricePerSheet строкой, только DRAFT, аудит в транзакции |

Это минимальный критический метод для проверки реальных прав, а не полный CRUD тарифов. Прямой доступ к внутренним функциям из client-компонентов запрещён. Входной JSON ограничен 4 KiB, цена валидируется как точное десятичное значение; объекты ролей/permissions и другие неизвестные поля не принимаются.

## Ограничение попыток и аудит
PostgreSQL атомарно считает все попытки: до 5 за 15 минут на нормализованный email и до 30 в минуту глобально. Тот же лимит действует для несуществующего email и на всех экземплярах приложения. IP/forwarded-заголовки не используются как доверенная идентичность, новый Redis/сервис не нужен. После лимита — 429 с Retry-After.

Аудит включает bootstrap, успешный/неуспешный вход, ограничение попыток, выход, отказ в праве, неподдерживаемую мутацию и изменение тарифа с прежним/новым значением. Нет паролей, хешей пароля, cookie или токенов; для ошибочного email — только хеш нормализованного адреса. Сроки хранения аудита и периодическая очистка истёкших сессий/старых throttle-строк — эксплуатационная настройка до запуска.

## Конфигурация и проверка
DATABASE_URL — существующий Supabase PostgreSQL. APP_ORIGIN — точный origin приложения (например http://localhost:3000 в dev, обязательно https://... в production). Неподходящий/missing production origin блокирует изменяющие запросы. В рабочем размещении HTTPS обязателен; deployments на этом этапе нет.

Миграция 20261103080000_admin_auth добавляет OPERATOR, AdminCredential, AdminSession и LoginThrottle; RLS без публичных политик включён. Существующие клиентские User и seed не получают пароль или роль администратора.

pnpm test проверяет хеширование/права и архитектурные границы. Интеграционный pnpm auth:test требует локальный AUTH_TEST_BASE_URL, APP_ORIGIN и отдельную DATABASE_TEST_URL с применёнными миграциями/seed, без пользователей/клиентов/заказов. Он создаёт только синтетических сотрудников со случайными паролями; на рабочей БД его запускать нельзя.

Проверки охватывают гостя/RSC/API, generic ошибки входа, cookie, отказ оператору, явное право, запрет повышения роли, актуальность ролей/версии пароля, лимиты, CSRF, logout/replay и отсутствие секретов в аудите. HTTP-набор передаёт cookie вручную и проверяет Secure-флаг. Дополнительно Chrome проверил production-сборку через локальный HTTPS-прокси с одноразовым самоподписанным сертификатом: вход/выход, реальную HttpOnly/Secure cookie, отсутствие токена в document.cookie и мобильную форму 320px. Это не проверка сертификата или конфигурации рабочего размещения.
