# Решения

Дата: 2026-11-03. Требования основаны на текущем запросе; полное ТЗ отсутствует.
См. [прогресс](PROGRESS.md) и [архитектуру](ARCHITECTURE.md).

## Зафиксированные ограничения
- Cloudflare — хостинг интерфейса и статических ресурсов. Workers и R2 не включать без отдельного обоснования.
- Supabase — единственный PostgreSQL; не создавать Railway PostgreSQL или другую параллельную БД.
- Для макетов и клиентских загрузок выбран один владелец: Supabase Storage с приватными bucket. Cloudflare хранит только сборку/публичные ресурсы интерфейса, не копии макетов. R2 не нужен на старте.
- Общий Node.js backend и Telegram-бот планируются на Railway при переходе к реализации, без запуска сервиса сейчас. Бот — транспорт к общему прикладному слою, а не отдельный владелец бизнес-правил.
- Supabase Auth применять по необходимости для сайта/сотрудников после выбора входа; не вводить второй независимый сервис идентификации. Telegram identity привязывать к внутреннему пользователю только после серверной проверки.
- Секреты только в окружении. Привилегированные ключи и токен бота доступны исключительно серверу.

## Предложение стека, не окончательная фиксация
Существующего кода и ограничений совместимости нет. Рабочий кандидат — TypeScript, React и статическая сборка (например Vite) для сайта/Mini App/админки; общий Node.js API для всех каналов.
Tailwind возможен как инструмент оформления, но не обязателен. Prisma оценить для Node.js после определения схемы и подключения к Supabase; ORM и версии пока не выбраны.

Next.js не утверждён автоматически: статический export подходит Cloudflare Pages, но серверные возможности требуют другого runtime. Для MVP с отдельным общим API необходимость SSR пока не доказана. Если подтвердится SEO/SSR-сценарий, отдельно проверить актуальную интеграцию Cloudflare и её ограничения; не переносить туда дублирующую бизнес-логику.

## Безопасность и воспроизводимость
- Цена и допустимость параметров определяются сервером; тарифы версионируются. Snapshot заказа хранит параметры, ставки, версию формулы, валюту, правила округления и итог.
- Согласование относится к конкретной неизменяемой версии файла; новая версия требует нового согласования.
- Доступ определяется ролью и принадлежностью заказа. Клиент не назначает себе роли и не утверждает цену.
- Авторизация backend обязательна даже при наличии RLS. Политики Storage/RLS не должны давать публичный доступ к макетам.
