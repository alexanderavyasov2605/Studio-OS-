# Решения

Дата: 2026-11-03. На этапе 3 пользователь предоставил ТЗ v1.0, сохранённое в docs/STUDIO_OS_MVP_TZ.md. Ранние разделы ниже фиксируют решения до получения этого документа.
См. [прогресс](PROGRESS.md) и [архитектуру](ARCHITECTURE.md).

## Первый просмотр текущей версии
- Пользователь поручил подготовить production и посмотреть текущую версию до следующего блока. Прежний запрет deployment относился к предыдущим этапам.
- Текущий SSR и общий Node.js backend размещаются одним сервисом Railway, БД — существующий новый Supabase пользователя. Для первого просмотра HTTPS-домен Railway; собственный домен/Cloudflare подключаются отдельно, Workers и вторая БД не создаются.
- Ветка release/production-review основана на этапе 5; main и предыдущие ветки не мержить. Dockerfile, readiness и preflight описаны в DEPLOYMENT.
- Railway UI сообщает, что старый Config as Code не доступен новым сервисам; параметры release задаются в панели, устаревший railway.json не используется.

## Этап 5: каталог
- server/catalog владеет чтением, валидацией и изменением каталога; server/auth — единой транзакционной проверкой сессии и прав. ADMIN или явное catalog:write для записи, OPERATOR по умолчанию только читает.
- ProductMaterial описывает витринные материалы отдельно от ProductCompatibility с реальным ProductionProfile. AUTO_SHEET/MANUAL_REQUEST не выдают непроверенную цену.
- Изображения: URL + alt + порядок, до шести. Стартовые SVG — иллюстрации. Файлы студии предварительно размещаются в Supabase Storage; загрузчик и новый сервис хранения не добавляются.
- Товар, изображения, материалы и аудит сохраняются атомарно; revision предотвращает потерю одновременных изменений. Публичное чтение динамическое. Seed сохраняет идентичность товара после правки slug.
- Начальные плёнки требуют ручного расчёта; бумажные наклейки, бирки и простые карточки отмечены листовыми. Калькулятор и форма заявки остаются за границей этапа.
- Windows: scripts/next.mjs запускает обычный Next CLI; узкий preload повторяет временный EPERM mkdir только внутри .next-auth и распознаёт уже существующую директорию. Права/ACL не меняются, остальные ошибки сохраняются. На других ОС preload не включается.

## Зафиксированные ограничения
- Cloudflare — хостинг интерфейса и статических ресурсов. Workers и R2 не включать без отдельного обоснования.
- Supabase — единственный PostgreSQL; не создавать Railway PostgreSQL или другую параллельную БД.
- Для макетов и клиентских загрузок выбран один владелец: Supabase Storage с приватными bucket. Cloudflare хранит только сборку/публичные ресурсы интерфейса, не копии макетов. R2 не нужен на старте.
- Общий Node.js backend и Telegram-бот планируются на Railway при переходе к реализации, без запуска сервиса сейчас. Бот — транспорт к общему прикладному слою, а не отдельный владелец бизнес-правил.
- Supabase Auth применять по необходимости для сайта/сотрудников после выбора входа; не вводить второй независимый сервис идентификации. Telegram identity привязывать к внутреннему пользователю только после серверной проверки.
- Секреты только в окружении. Привилегированные ключи и токен бота доступны исключительно серверу.

## Предложение стека, не окончательная фиксация
Существующего кода и ограничений совместимости нет. Рабочий кандидат — TypeScript, React и статическая сборка (например Vite) для сайта/Mini App/админки; общий Node.js API для всех каналов.
Tailwind возможен как инструмент оформления, но не обязателен. Prisma оценить для Node.js после определения схемы и подключения к Supabase; ORM и версии пока не выбраны.

Next.js не утверждён автоматически: статический export подходит Cloudflare Pages, но серверные возможности требуют другого runtime. Для MVP с отдельным общим API необходимость SSR пока не доказана. Если подтвердится SEO/SSR-сценарий, отдельно проверить актуальную интеграцию Cloudflare и её ограничения; не переносить туда дублирующую бизнес-логику.

## Безопасность и воспроизводимость
- Цена и допустимость параметров определяются сервером; тарифы версионируются. Snapshot заказа хранит параметры, ставки, версию формулы, валюту, правила округления и итог.
- Согласование относится к конкретной неизменяемой версии файла; новая версия требует нового согласования.
- Доступ определяется ролью и принадлежностью заказа. Клиент не назначает себе роли и не утверждает цену.
- Авторизация backend обязательна даже при наличии RLS. Политики Storage/RLS не должны давать публичный доступ к макетам.

## Этап 1: уточнение стека по заданию пользователя
Запрос от 2026-11-03 фиксирует Next.js App Router, TypeScript strict, Tailwind CSS, PostgreSQL/Prisma и pnpm вместо прежнего предложения React/Vite. Стек выбран для основы, без реализации предметной области.
Prisma 7 использует prisma.config.ts; схема не содержит бизнес-моделей, миграций и обращений к БД. Привилегированные данные не попадают в UI.
Локальная Node.js сборка допускает произвольный /configure/[slug]. Cloudflare deployment не реализован: до него выбрать генерацию известных slug для static export либо обосновать Workers/адаптер для динамического маршрута. Стандартный next build не означает совместимость с Pages.
Дублирующий backend, API routes, Server Actions и Prisma-вызовы из страниц не добавляются.
ESLint 9.39.5 закреплён, поскольку eslint-plugin-import/react/jsx-a11y в текущем eslint-config-next не заявляют совместимость с ESLint 10. Реестр помечает ESLint 9 как deprecated; обновить вместе с совместимым набором плагинов.

## Этап 2: единая дизайн-система
- Расширены существующие React/Tailwind-компоненты без установки UI-библиотек. Токены в app/globals.css, общие компоненты в components/ui; серверная архитектура не меняется.
- Шрифт Inter при наличии, иначе Segoe UI/system-ui, без внешней загрузки. Акцент #7C3AED; статусы дополняются текстом и значком, не только цветом.
- /ui-kit — только development, production всегда notFound. NODE_ENV проверяется единожды в серверной странице как режим сборки; это не авторизация и не обращение к секретам. Тест границы допускает только эту конкретную проверку.
- Мини-приложение перенесено из публичного route group в app/mini для собственной оболочки. URL /mini сохранён, Telegram/backend не добавляются.
- Визуальные статусы — словарь отображения, не реализация серверных переходов заказов. Подробнее: [DESIGN_SYSTEM](DESIGN_SYSTEM.md).

## Этап 3: модель данных
- Принято предоставленное пользователем [ТЗ v1.0](STUDIO_OS_MVP_TZ.md); исходный файл сохранён без изменений. Currency по ТЗ — UZS. Роли включают дизайнера и владельца.
- Минимальная схема — 24 модели: обязательные сущности плюс версии прайсов, позиции расчёта, совместимость и включённые операции. ProductionProfile соответствует EquipmentProfile из ТЗ; дополнительные сущности полного MVP пока не реализуются.
- Decimal(18,2) для сумм, Decimal(18,4) для ставок, Decimal(10,3) для мм, timestamptz(3) для дат. JSONB snapshot сохраняет коммерческие данные независимо от редактируемого каталога.
- Опубликованный прайс не редактируется; нужен новый DRAFT. Финансовые связи защищены от каскадного удаления; Customer можно отсоединить без потери истории.
- Пользовательские SQL-инварианты и RLS находятся в миграции. Не использовать db push как замену миграциям. Ни HTTP API, ни UI, ни отдельный сервис БД не создаются.

## Этап 4: авторизация сотрудников
- Один server/auth в общем Node.js backend; Next.js Proxy, серверные страницы и служебный Route Handler — адаптеры. Бизнес-правила не копируются между транспортами.
- Сотрудники ADMIN/OPERATOR используют отдельную Credential в том же PostgreSQL. Никакой публичной регистрации или Telegram-авторизации. Первый ADMIN — только CLI bootstrap с паролем из окружения, без повышения существующего User.
- Выбраны native scrypt, opaque 256-bit session token с хешем в БД, абсолютный срок 8 часов, отзыв при logout и актуальные роли/права при каждом запросе. Cookie production: __Host-, HttpOnly, Secure, SameSite=Strict.
- Попытки входа ограничиваются PostgreSQL, без Redis и доверия клиентскому IP. CSRF проверяется по точному APP_ORIGIN. Аудит и критическое изменение тарифа — одна транзакция.
- Сборка/dev используют Webpack: Turbopack в текущей Windows-среде требует недоступные junction для pg. Каталог .next-auth выделен для новых артефактов без удаления старого кеша; конфигурация описана в README.
- Полный контракт и пределы этапа: [AUTH](AUTH.md).
